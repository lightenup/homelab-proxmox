# Implementation Plan: Monitoring Tier C — Security & Availability Probing

**Branch**: `042-monitoring-tier-c` | **Date**: 2026-03-02 | **Spec**: [spec.md](spec.md)
**Input**: Feature specification from `specs/042-monitoring-tier-c/spec.md`

## Summary

This feature adds security and availability monitoring to the homelab: HTTPS endpoint probing with TLS certificate lifecycle tracking (via Prometheus blackbox_exporter), brute-force detection and blocking (via fail2ban on 3 LXC hosts), fail2ban metrics collection (via hctrdev fail2ban-prometheus-exporter), a consolidated Security Overview Grafana dashboard, 6 new alert rules, and 4 new inhibition rules. All components are deployed via Ansible, following the existing monitoring stack patterns from Features 040 and 041.

## Technical Context

**Language/Version**: Ansible (YAML), Jinja2 templates, PromQL, Grafana JSON
**Primary Dependencies**: Prometheus v3.8.1, Grafana 12.3.1, Alertmanager v0.30.0, blackbox_exporter v0.28.0, fail2ban (Debian apt), fail2ban-prometheus-exporter v0.10.3
**Storage**: Prometheus TSDB (existing, no changes)
**Testing**: `promtool check rules` (existing validate_alerts.yml task), `ansible-playbook --check`, manual verification via curl/API
**Target Platform**: Proxmox LXC containers (Debian stable)
**Project Type**: IaC (Ansible roles + playbooks)
**Performance Goals**: Probe interval ≤30s, alert delivery <5 minutes, dashboard load <5s
**Constraints**: <50 MB RAM per component, no public exposure of metrics endpoints
**Scale/Scope**: 5 HTTPS probe targets, 3 fail2ban hosts (5 jails total), 1 dashboard, 6 alerts, 4 inhibitions

### Step 1: Create fail2ban Ansible Role — Defaults and Handlers

- **Files**: `ansible/roles/fail2ban/defaults/main.yml`, `ansible/roles/fail2ban/handlers/main.yml`
- **Description**: Create the fail2ban role skeleton with version pins, port assignments, and path defaults. Define handlers for restarting fail2ban and the exporter.
- **Traces to**: FR-009, FR-013, FR-014
- **Dependencies**: None
- **Parallel-safe**: Yes (with Step 2, Step 3)

**Defaults include**:
- `fail2ban_exporter_version: "0.10.3"`
- `fail2ban_exporter_port: 9191`
- `fail2ban_exporter_install_dir: "/opt/fail2ban-exporter"`
- `fail2ban_exporter_arch: "linux_amd64"` (underscore — matches GitLab release asset naming)
- `fail2ban_socket_path: "/var/run/fail2ban/fail2ban.sock"`
- `fail2ban_sshd_maxretry: 5`, `fail2ban_sshd_bantime: 3600`, `fail2ban_sshd_findtime: 600`

**Done-condition**: File exists with all required variables defined. `ansible-playbook --syntax-check` passes on a playbook referencing this role.

### Step 2: Create fail2ban Filters — Nextcloud and Jellyfin

- **Files**: `ansible/roles/fail2ban/files/filter.d/nextcloud.conf`, `ansible/roles/fail2ban/files/filter.d/jellyfin.conf`
- **Description**: Create fail2ban filter definitions for Nextcloud JSON auth failure logs and Jellyfin auth denial logs. sshd filter ships with fail2ban — no custom filter needed.
- **Traces to**: FR-011, FR-012
- **Dependencies**: None
- **Parallel-safe**: Yes (with Step 1, Step 3)

**Nextcloud filter** (`failregex`): Matches JSON log entries with `remoteAddr` and "Login failed:" or "Trusted domain error." messages.

**Jellyfin filter** (`failregex`): Matches `Authentication request for .* has been denied (IP: "<ADDR>")`.

**Done-condition**: Files exist with syntactically valid fail2ban filter definitions (regex patterns include `<HOST>` or `<ADDR>` capture groups).

### Step 3: Create fail2ban Templates — Jail Config and Exporter Service

- **Files**: `ansible/roles/fail2ban/templates/jail.local.j2`, `ansible/roles/fail2ban/templates/fail2ban-exporter.service.j2`
- **Description**: Create Jinja2 templates for fail2ban jail configuration (iterates over `fail2ban_jails` list from host_vars) and the exporter systemd service unit.
- **Traces to**: FR-009, FR-010, FR-011, FR-012, FR-014
- **Dependencies**: Step 1 (needs defaults)
- **Parallel-safe**: Yes (with Step 2)

**jail.local.j2**: Iterates over `fail2ban_jails` list variable (defined per-host in host_vars). Each jail entry specifies: name, filter, logpath, maxretry, bantime, findtime. The sshd jail uses the built-in filter; nextcloud and jellyfin use custom filters from Step 2.

**fail2ban-exporter.service.j2**: systemd unit with `ExecStart={{ fail2ban_exporter_install_dir }}/fail2ban_exporter --socket {{ fail2ban_socket_path }} --web.listen-address :{{ fail2ban_exporter_port }}`. Follows the jellyfin-exporter.service.j2 pattern (NoNewPrivileges, Restart=on-failure).

**Done-condition**: Templates render without Jinja2 errors when provided test variables.

### Step 4: Create fail2ban Role — Main Tasks

- **Files**: `ansible/roles/fail2ban/tasks/main.yml`
- **Description**: Implement the fail2ban deployment task sequence: install fail2ban via apt, deploy custom filters, deploy jail configuration from template, start fail2ban service, download exporter binary, deploy exporter systemd service, start exporter service.
- **Traces to**: FR-009, FR-010, FR-011, FR-012, FR-013, FR-014, FR-016, FR-026
- **Dependencies**: Steps 1, 2, 3
- **Parallel-safe**: No

**Task sequence**:
1. `apt install fail2ban` (state: present)
2. Deploy custom filter files from `files/filter.d/` → `/etc/fail2ban/filter.d/`
3. Deploy `jail.local.j2` → `/etc/fail2ban/jail.local`
4. Enable and start fail2ban service
5. Create exporter install directory
6. Download exporter binary archive from GitLab releases (`https://gitlab.com/hctrdev/fail2ban-prometheus-exporter/-/releases/v{{ fail2ban_exporter_version }}/downloads/fail2ban_exporter_{{ fail2ban_exporter_version }}_{{ fail2ban_exporter_arch }}.tar.gz`)
7. Extract exporter binary (binary name inside tarball: `fail2ban_exporter`)
8. Set executable permissions
9. Deploy exporter systemd service from template
10. Enable and start exporter service

**Done-condition**: `ansible-playbook --syntax-check playbooks/fail2ban.yml` passes. Role tasks follow the same pattern as `ansible/roles/jellyfin/tasks/main.yml` for exporter deployment.

## Risk Assessment

| Risk | Impact | Mitigation |
|------|--------|------------|
| DNS `*.hus-sky.no` doesn't resolve from monitoring LXC | All HTTPS probes fail, 5 EndpointDown alerts fire | Verify DNS resolution as prerequisite before deployment (A-002). Document in quickstart.md. |
| Nextcloud log path changes or NAS unavailable | nextcloud fail2ban jail non-functional | FR-011 contingency clause: sshd jail still operates. Log path derived from confirmed Docker Compose volume mapping. |
| Jellyfin log level not set to Information | jellyfin fail2ban jail doesn't catch auth failures | Add logging config check/set task in fail2ban role for Jellyfin. FR-012 contingency clause: sshd jail sufficient. |
| fail2ban exporter download URL changes (GitLab) | Role fails during exporter deployment | Pin version in defaults. Use checksum verification. Binary archive URL is stable for tagged releases. |
| Blackbox exporter can't reach Caddy from Docker network | HTTPS probes fail for all endpoints | Blackbox runs in Docker with host network access (ports mapped). Caddy IP (192.168.1.211) is LAN-accessible from monitoring LXC. |
| New inhibition rules conflict with existing ones | Unexpected alert suppression | New rules use distinct alert names (EndpointDown, Fail2banDown) that don't overlap with existing source alerts (SynologyNASDown, ServiceDown). |
| Stale probe data when blackbox crashes | 5 EndpointDown alerts fire (spec edge case) | Rely on ServiceDown alert for blackbox-exporter scrape target. `for: 2m` threshold absorbs brief restarts. |
