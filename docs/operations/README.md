# Operations Manual

## Operator vs Rebuild-Critical Tasks

This repo distinguishes between:

- **Rebuild-critical** tasks: part of the infrastructure rebuild path, safe to automate (e.g. `terraform:validate`, `deploy:lab`, `inventory:update`).
- **Operator-only** tasks: day-to-day maintenance that may depend on local context (e.g. `service:add`, `healthcheck:run`, `summary:render`).

The operator-facing entrypoint is the repo-root Taskfile (`task` command). Run `task -l` to discover available workflows.

Deprecation and shim rules: [tooling-sunsetting.md](tooling-sunsetting.md)

## Service Promotion Workflows

Preferred day-to-day deployment path is via bounded GitHub Actions promotion workflows:

- **LAB-only**: `.github/workflows/lxc-promote-lab.yml` (plan+apply to LAB; never touches PROD)
- **PROD pipeline (plan + evidence)**: `.github/workflows/lxc-promote-prod.yml` (explicit `ref` checkout -> LAB apply -> best-effort confidence suite -> PROD plan -> publish summaries + metadata artifact)
- **PROD apply (manual gate)**: `.github/workflows/lxc-apply-prod.yml` (manual workflow_dispatch that applies PROD from the saved plan generated by the promotion run)
- **Unified lifecycle**: `.github/workflows/lxc-lifecycle.yml` (single entrypoint for add/change/delete with plan + apply)

Operational notes:

- The PROD pipeline always attempts to generate a PROD plan (even if LAB deploy or the confidence suite fails).
- This repo's billing plan does not support GitHub Environment required reviewers for interactive in-workflow approvals; the approval gate is implemented as a separate manual workflow dispatch.
- PROD apply uses the saved plan RUN_ID from the plan stage (`--from-plan-run-id <prod_plan_run_id>`), and enforces LAB gate + SHA alignment + destructive confirmations using the promotion run metadata artifact.

### Unified Lifecycle Gates

- **Destructive changes** require an explicit tag (input: `confirm_destructive_tag`) pointing at the commit being applied.
- **Maintainer scope** is defined in [.github/CODEOWNERS](../../.github/CODEOWNERS) and does not require paid GitHub features.
- **Data deletion** for `action=delete` requires `confirm_data_delete=delete-data`.
- **Prod apply** still requires `confirm_apply_prod=deploy-prod` and `ALLOW_PROD_APPLY=1` on PVE.

## Proxmox CI Posture

- CI user only: all SSH/rsync from workflows must target `ci@pve` with non-interactive sudo; root SSH is disallowed.
- Ansible defaults: use `remote_user=ci` with `become_flags=-n`; avoid `remote_user: root` except bootstrap.
- Terraform: use a non-root Proxmox API token (e.g., `ci-terraform@pve!token`) provided via `TF_VAR_proxmox_api_token_id`/`TF_VAR_proxmox_api_token_secret`.

Details: [proxmox-ci.md](proxmox-ci.md)

## Evidence Governance

The lab suite produces evidence packs for every run. These packs are validated against a strict schema and catalog.

### Verification

```bash
scripts/lab/pve-lab verify-evidence artifacts/019-lab/lab-YYYYMMDD-HHMMSS
```

This checks: JSON schema compliance, catalog coverage, and file integrity.

### Comparison (Diff)

```bash
scripts/lab/pve-lab diff-evidence artifacts/019-lab/run-A artifacts/019-lab/run-B
```

### Catalog Maintenance

The Check Catalog is the Single Source of Truth (SSOT) for all checks.
Location: `scripts/lab/checks.d/catalog.json`

To add a new check:
1. Add the check definition to `catalog.json`.
2. Ensure the `check_id` is unique.
3. Run `scripts/lab/ci-verify.sh` to validate the catalog.
